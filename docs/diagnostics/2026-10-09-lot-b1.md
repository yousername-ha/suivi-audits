# Diagnostic technique — B1, activation des modules

Branche exclusive : `feature/gpt6-evolution-smsi-grc`. Diagnostic établi avant modification fonctionnelle.

Le socle dispose de quinze modules de permissions, de rôles versionnés, d'une garde HTTP commune, d'un filtrage des données historiques par clé, d'import/export transactionnels et de notifications PostgreSQL/SSE. Les modules v2 restent dans l'état historique ; la cartographie est déjà reprise en tables. Les menus Sauge utilisent les permissions, mais l'activation globale d'un module n'existe pas. L'interface historique possède des groupes mixtes : masquer uniquement un groupe laisserait des sous-menus accessibles.

La planification d'audit utilise les mesures et le cycle du module audit : sa dépendance est obligatoire. Les rattachements aux écarts, processus, fournisseurs, documents et cartes sont des enrichissements facultatifs ; ils ne doivent pas imposer la suppression ou la désactivation du reste du socle.

L'authentification, les comptes et droits, le journal d'audit, les paramètres de sécurité, la base et les opérations de sauvegarde/restauration du lot A sont fondamentaux. Administration et paramètres restent activés. L'audit métier peut être désactivé : il est distinct du journal de sécurité.

## Évolution prévue

Un registre commun fournit les identifiants existants, les dépendances obligatoires et facultatives et les protections. Une migration additive crée une configuration versionnée, tous les modules actifs par défaut. Prévisualisation explicite des conséquences, puis confirmation liée à la version et à l'empreinte de la prévisualisation ; refus des désactivations protégées et des dépendances rompues. Une cascade doit être demandée et apparaître dans la prévisualisation.

L'activation complète les permissions sans modifier les attributions de rôles. La garde commune bloque les routes d'un module désactivé ; les chemins transversaux (état historique, synthèse, affichage mural, imports, téléchargement brut, restauration historique et paramètres métier) doivent appliquer la même politique. Les données et configurations restent stockées et retrouvent leur visibilité lors de la réactivation. Les menus historiques sont adaptés à l'exécution, sans réécriture du fichier source v2 ni changement de la charte Sauge.

Les écritures métier et les changements d'activation partagent un verrou PostgreSQL : une confirmation ne peut pas dépasser une écriture déjà engagée et une requête ancienne ne peut pas écrire après la désactivation. Un pool de verrous séparé et borné évite de monopoliser les connexions des transactions métier.

Les notifications d'activation sont publiques pour les sessions authentifiées, sans contenu métier. Les données du cache navigateur et les droits affichés doivent être renouvelés, y compris après reconnexion SSE. Le flux serveur filtre les événements avec la configuration actuelle.

## Effets opérationnels

Les sauvegardes, restaurations de secours, contrôles TLS et tâches de sécurité continuent : ce sont des fonctions fondamentales. Le socle actuel n'exécute pas de tâches métier autonomes ni d'intégrations externes ; toute future tâche devra vérifier l'activation avant son exécution. Les imports et retours arrière historiques sont refusés s'ils portent sur un module désactivé. Une désactivation ne déclenche aucune suppression de données, de configuration, de documents ou de planification.

## Validation attendue

Tests du graphe, des cascades et protections ; API avec PostgreSQL réel pour les droits, MFA/CSRF, confirmations, versions concurrentes, conservation/réactivation, chemins transversaux et verrouillage ; contrôle des menus et du temps réel ; suites de non-régression et CI GitHub complète. Aucun renouvellement automatique des captures visuelles. PR ouverte vers main, sans fusion.

## Résultat local

Le registre de quinze modules, la migration additive 008, les routes de configuration et l'écran Administration > Système sont implémentés. Les droits, données, configurations et références restent conservés. Les chemins transversaux et les deux interfaces utilisent les modules actifs ; les caches privés sont réinitialisés sur notification et reconnexion.

La recette a détecté une hypothèse de l'ancien tableau de bord : l'objet IA doit contenir ses tableaux même lorsqu'il est masqué. L'adaptateur fournit désormais une structure neutre, filtre aussi le bloc initial HTML et conserve les données lors des enregistrements. Le fichier source v2 et les captures de référence sont inchangés.

Validation locale : **203 tests partagés, 171 tests API PostgreSQL 17, 102 tests UI et 16 tests web réussis**. Les quatre scénarios navigateur vérifient la prévisualisation mobile et les dépendances, la confirmation et le blocage API, la conservation à la réactivation, les sous-menus v2 mis à jour par SSE et les transferts désactivés. Une recette complémentaire désactive puis réactive chacun des treize modules non protégés sans erreur du tableau de bord v2. Les tests web utilisent un observateur actif du cache pour vérifier la disparition des anciennes données privées. La CI exécute également les suites web et UI.

La recette GitHub a détecté un écart de masques de dates sur la fiche documentaire mobile. Le premier contact SSE réinitialisait même les données venant d'être chargées avec les mêmes droits. Il reconsulte désormais la session et conserve le cache lorsque les droits sont identiques ; les droits modifiés, reconnexions et notifications imposent toujours la purge. Ces cas sont couverts par les tests web. Les références visuelles et leur seuil restent inchangés.

Le lot B2 (paramétrage métier central et versionné) reste à réaliser. Le lot B1 ne modifie pas les échelles ni les matrices métier existantes.
