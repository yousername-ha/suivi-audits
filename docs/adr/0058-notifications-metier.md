# ADR 0058 — Notifications métier : réglage par groupe, rôle et utilisateur, application et courriel

- Statut : acceptée
- Date : 2026-10-26
- Contexte : décision 012-10 de l'utilisateur (26/10/2026) : « Application + courriel (si configuré), réglage par groupe, profil, utilisateur. Si le groupe est coché alors c'est coché pour tous les utilisateurs du groupe, sauf si je décoche directement dans le profil de l'utilisateur : alors cela prend le dessus sur le droit du parent. Si A, B, C sont dans le groupe et que j'ai coché la notification mail, mais que dans le profil utilisateur de A j'ai retiré la notification mail, alors seuls B et C reçoivent la notification. L'utilisateur a la main dans son profil aussi. » S'appuie sur l'[ADR 0049](0049-courriel-et-sortie-reseau-optionnelle.md) (l'API n'envoie rien, l'exécutant d'exploitation envoie) et sur les groupes, fonctions et rôles ([ADR 0010](0010-droits-rbac.md), [ADR 0043](0043-registres-perimetres-herites-et-droits-par-ressource.md)). Règle du projet : tout se configure dans l'interface, aucun fichier.

## Ce qui existait

La table `grc_notifications` (migration 013) est remplie par trois émetteurs seulement, tous dans le serveur : `task_due` (rappel d'échéance d'une action, au responsable ou aux membres du groupe ou de la fonction responsable), `risk_review` (réévaluation périodique d'un risque, au propriétaire) et `rapprochement` (rapprochements à valider, aux pilotes de la mesure). Ils s'affichent dans Pilotage > Rappels. Il n'existe **ni** type « retard », **ni** type « affectation » : la liste fermée du paquet partagé ne contient que ces trois types réellement émis. Aucun courriel ne partait.

## Décision

1. **Types et canaux** : liste fermée dans `packages/shared/src/notifications.ts` (identifiant, libellé, description). Canaux : `application` et `courriel`. Valeur par défaut : application activée, courriel désactivé (le comportement antérieur est donc inchangé tant que rien n'est réglé).
2. **Trois portées, tri-état** « activé », « désactivé », « non défini (hérite) » par (portée, type, canal) : **groupe**, **rôle** et **utilisateur**. Une ligne de `notification_reglages` = un réglage explicite ; pas de ligne = non défini. Une version par portée (`notification_portees`) sert d'ETag : toute écriture exige `If-Match`, un conflit renvoie 412 avec l'état courant.
3. **« Profil » = rôle.** Le dépôt n'a pas d'objet « profil » distinct : un compte a des rôles (directs ou portés par ses groupes, ADR 0010), et la « fiche » d'un utilisateur est sa fiche de compte. Le réglage « par profil » de la décision est donc le réglage **par rôle** ; le « profil utilisateur » où l'on décoche est la fiche du compte (administration) ou Mon compte (la personne elle-même). Les fonctions de l'ADR 0043 ne sont pas une portée de réglage : elles désignent des responsables, pas des droits.
4. **Règle de résolution** (fonction pure `resoudreNotification`, testée dans le paquet partagé), dans cet ordre :
   a. si l'utilisateur a un réglage explicite (activé ou désactivé) pour (type, canal), il l'emporte **toujours** ;
   b. sinon, **activé si au moins un** de ses groupes ou de ses rôles est explicitement activé (un autre groupe ou rôle désactivé ne retire rien) ;
   c. sinon la valeur par défaut.
   **Écart documenté** : le cahier des charges ne dit rien d'un groupe ou rôle explicitement **désactivé** quand aucun autre n'est activé. Pour qu'un « désactivé » de groupe ou de rôle ait un effet (par exemple couper l'application pour un groupe), la règle (b) est complétée : si aucun groupe ni rôle n'est activé mais qu'au moins un est explicitement désactivé, le résultat est **désactivé**. L'« activé » l'emporte donc toujours sur le « désactivé » entre parents, et le réglage personnel l'emporte sur tous. Les rôles d'un compte sont ceux qu'il détient directement et ceux de ses groupes ; l'origine affichée cite le groupe en premier, puis le rôle.
5. **Cas de la décision** (test partagé et test d'API) : A, B et C sont dans un groupe dont le courriel est coché ; A l'a retiré dans son profil ; seuls B et C reçoivent le courriel, A garde l'application.
6. **Diffusion** (`NotificationsMetier.diffuser`, appelé dans la transaction de chaque émetteur, uniquement pour les lignes réellement créées) :
   - la notification est **toujours enregistrée** dans `grc_notifications` : c'est elle qui empêche le doublon au passage suivant. Le canal application ne décide que de sa **visibilité** (colonne `canal_application`, migration 044) : désactivé au moment de l'émission, elle n'apparaît pas dans Rappels. Changer un réglage n'agit pas sur les notifications déjà émises ;
   - le canal courriel dépose une demande de type `notification` dans la file `courriel_jobs` **seulement si** le courriel est activé, avec un hôte et une adresse d'expédition (même contrôle que l'ADR 0049). Sinon, le réglage reste enregistrable, l'interface dit « Courriel non configuré, rien n'est envoyé » et **aucune demande n'est tentée ni mise en file**.
7. **File et exécutant.** `courriel_jobs` gagne : `kind = 'notification'`, `notification_id`, `user_id`, `subject`, `body` ; index unique `(notification_id, user_id)` : **aucun doublon**, même si la diffusion est rejouée. Pas de demande pour un compte désactivé, expiré ou sans adresse utilisable (contrôlé au dépôt, puis **relu au moment de l'envoi** : adresse courante, compte encore actif, sinon la demande est close « rien n'a été envoyé » et la suivante est réclamée). L'exécutant (`scripts/exploitation-worker.py`) traite jusqu'à **20 demandes ou 150 secondes par passage** (`mails()`), le message de test passe avant les notifications ; le reste attend le passage suivant. Une demande de notification en attente depuis plus de **3 jours** est abandonnée. L'envoi reste fait par `scripts/courriel-envoi.py` sous le compte sans privilège, avec le même contrôle strict (TLS, objet sans saut de ligne, taille bornée) ; la trace d'une notification ne contient **pas l'adresse** du destinataire, et `to_address` est vidé quand la demande est terminée. Un échec est tracé dans la demande (état `echec` et explication) ; il n'affecte jamais la notification dans l'application. Aucune relance automatique.
8. **Contenu du courriel** : objet « <nom de l'application> : <libellé du type> », corps en texte brut français : un titre court, un lien vers la rubrique Pilotage > Rappels (adresse du site + chemin relatif `/pilotage/rappels`), un rappel de la raison de l'envoi et de l'endroit où modifier ses réglages. **Aucune donnée métier** : ni nom d'action, de mesure ou de risque, ni échéance, ni détail.
9. **Interface** (aucun fichier à éditer) :
   - **Administration > Plateforme > « Destinataires des notifications »** (lecture : `administration:lire`, écriture : `administration:administrer`) : choix d'un groupe ou d'un rôle, matrice type × canal en tri-état écrit en toutes lettres, bandeau d'état du courriel, synthèse des envois des sept derniers jours (sans adresse), et **aperçu « qui recevrait quoi »** pour un type et un canal : destinataires résolus avec leur origine (groupe, rôle, réglage personnel, valeur par défaut), comptes exclus par un réglage personnel, comptes sans adresse pour le courriel, nombre de comptes sans réglage actif. La carte « Notifications » existante ne garde que les délais d'alerte.
   - **Administration > Utilisateurs > Notifications** : réglages personnels du compte (tri-état) et résultat effectif avec son origine.
   - **Mon compte > Notifications** : la personne règle elle-même, par type et canal, voit le résultat effectif et son origine.
   L'information ne repose jamais sur la couleur seule (états écrits, `StatusChip` accompagné de texte) ; la charte et la CSP stricte sont respectées (test `charte.test.ts`).
10. **Droits et traçabilité.** `GET/PUT /api/account/notifications` : tout compte authentifié, **uniquement le sien** (l'identifiant n'est pas un paramètre). `…/api/admin/notifications/*` : `administration:lire` pour lire, `administration:administrer` pour écrire. Chaque écriture a son `If-Match`, n'enregistre que les différences, et écrit au journal d'audit (`notifications.reglages` ou `notifications.reglages_personnels`) l'auteur, la portée, la cible (nom du groupe, identifiant du rôle, identifiant de connexion du compte) et les couples type/canal avec l'ancienne et la nouvelle valeur ; **jamais d'adresse courriel**. La suppression d'un groupe, d'un rôle ou d'un compte emporte ses réglages (déclencheurs de la migration 044).

## Ce qui n'est pas fait

- Aucun type « retard » ni « affectation » : ils ne sont pas émis aujourd'hui (aucun invention de type). Les ajouter suppose un émetteur, puis une ligne dans la liste fermée.
- Pas de synthèse périodique (digest) ni de regroupement : un courriel par notification et par personne, dans la limite de débit.
- Pas de nouvelle tentative automatique ; une demande qui échoue reste en échec, consultable dans la carte d'administration (compte, jamais l'adresse).
- Le réglage est évalué à l'émission puis à l'envoi pour la seule validité du compte ; si une personne retire le courriel entre le dépôt et l'envoi (au plus quelques minutes), le message déjà en file part.
- Les notifications déjà émises ne sont pas masquées ni ré-évaluées quand un réglage change.
- Les demandes terminées de `courriel_jobs` ne sont pas purgées (ADR 0048 : aucune purge automatique) ; l'adresse y est effacée, l'objet et le corps (sans donnée métier) restent. Elles ne sont pas encore comptées dans l'aperçu de conservation.
- L'aperçu liste tous les comptes actifs concernés sans pagination (volumes d'une organisation : quelques centaines de comptes au plus).
- Non vérifié contre un serveur SMTP réel : les tests utilisent le faux serveur local de l'ADR 0049. La spécification Playwright `tests/e2e/specs/…-notifications.spec.ts` est écrite mais n'a pas été exécutée pendant le chantier.

## Conséquences

- Migration additive `044_notifications_metier.sql` (rejouable) : `notification_reglages`, `notification_portees`, déclencheurs de nettoyage, colonne `grc_notifications.canal_application`, extension de `courriel_jobs`.
- Aucune dépendance ajoutée. Aucune étape d'installation nouvelle ([guide, 11.8](../INSTALLATION.md)).
- `Courriel.demanderTest`, `derniere` et `lireDemande` se limitent désormais aux demandes de test : les notifications en file ne bloquent pas un message de test et n'apparaissent pas dans sa trace.
