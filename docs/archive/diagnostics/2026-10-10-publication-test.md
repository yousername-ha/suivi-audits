# Diagnostic de publication de la branche de test

Analyse avant toute évolution, depuis `661309c`, sur `feature/gpt6-evolution-smsi-grc` uniquement.

- Le dépôt GitHub est privé ; aucun tag ni release n'existait. La CI et CodeQL du socle G/H/K/début E sont réussis sur ce commit.
- L'API n'exécute aucune commande Docker. Les demandes administrateur passent par la file PostgreSQL puis l'exécutant isolé, avec contrôles de rôle, sauvegarde, maintenance, signatures, reprise et santé réelle.
- Le contrat de versions est `X.Y.Z` dans le schéma partagé, l'exécutant, les scripts serveur et les comparaisons de l'interface. Un tag suffixé `-dev` ne serait pas installable depuis le menu existant.
- La découverte publique utilise GitHub `/releases/latest` et refuse les préversions. Le chemin privé réutilise la clé Git, sélectionne la plus haute étiquette numérique et contrôle la présence des trois images. Il permet déjà une **préversion GitHub à numéro numérique**, sans changement de l'exécutant installé. Cette possibilité s'applique à tous les serveurs autorisés sur le dépôt, avec confirmation administrateur obligatoire.
- La confiance exige une signature issue de `release.yml@refs/tags/vX.Y.Z` et un label de révision égal au commit du tag. Une publication manuelle depuis une branche, sans cette chaîne, serait refusée.
- La chaîne initiale publiait les étiquettes d'images avant ses scans/signatures et mettait à jour l'alias mineur. La livraison de développement doit conserver les alias stables et exposer les trois étiquettes numériques seulement après tous les contrôles.

Décision : numéro de transport `3.0.1`, manifeste de développement versionné, tag depuis la branche de travail après CI/CodeQL verts, préversion GitHub explicite, images exactes scannées/signées, aucun alias stable ni changement de main. Aucun changement de l'authentification, des migrations, de l'interface ou de l'exécutant requis. Les installations locales doivent annoncer un numéro numérique inférieur à la cible ; les installations v2 nécessitent encore la montée de version serveur préalable. Un canal de test isolé ou les préversions d'un futur dépôt public nécessiteraient une évolution distincte.

## Reprise de publication

La tentative `v3.0.1` du commit `cc285b4`, après CI et CodeQL réussis, a échoué dans `actions/setup-node@v5` avant toute construction/publication d'image : le cache automatique découvre `packageManager: pnpm` mais pnpm n'est pas installé dans le job des notes, qui utilise seulement Node et Git. Le cache est désactivé explicitement pour ce job. L'étiquette existante reste immuable ; la publication suivante utilise `3.0.2`, avec les mêmes fonctionnalités et des contrôles sur son propre commit.

La première recette CI en présence de ce tag annoté a également révélé une assertion incorrecte dans `montee-version.sh` : après un retour arrière réussi, `rev-parse HEAD` (commit) était comparé à `rev-parse v3.0.1` (objet tag). La référence de départ est désormais résolue avec `^{commit}`. Le processus de retour arrière de production n'est pas modifié ; la recette vérifie les commits réellement exécutés, pour une référence SHA, un tag léger ou un tag annoté.

Une fois cette assertion corrigée, la migration simulée suivante a été refusée avant modification parce que la recette ne créait que les images API/web, sans l'image updater exigée par le contrat actuel. La recette prépare désormais ce troisième composant quand la version cible le comprend. Les erreurs de contrôle avaient en outre été masquées par une redirection persistante de stderr sur `exec` lors de l'ouverture du verrou ; la redirection est limitée au groupe qui ouvre ce verrou. Les verrous et le refus d'une image manquante sont conservés.

La recette suivante a franchi la mise à jour et la migration, mais le retour arrière CLI a rencontré le verrou de l'exécutant automatique. Le chemin web possédait déjà les deux verrous communs ; le script CLI ne les conservait pas entre sauvegarde et restauration. Il acquiert désormais les deux verrous avant sauvegarde, attend au maximum 120 secondes une opération active et les conserve jusqu'à la fin, en transmettant les descripteurs aux scripts enfants. Le chemin web réutilise ses descripteurs hérités ; aucune exclusion n'est désactivée.

Une reproduction dans le conteneur updater a ensuite révélé que BusyBox find ne comprend pas `-printf`, utilisé pour la rotation des archives par `mettre-a-jour.sh`. L'image doit fournir findutils comme l'hôte Ubuntu du guide et de la recette. Un ancien updater atteint cette rotation avant de se remplacer ; cette limitation impose un premier redéploiement de la branche, documenté dans INSTALLATION 12.0, sans désactiver signatures ou sauvegardes. La recette dans le vrai conteneur complète la recette hôte.

Validation locale des correctifs dans le vrai conteneur updater, avec poller automatique actif : sauvegarde chiffrée, migration fictive `999_reprise_cli_test.sql`, échec de santé volontaire, restauration effective et ancienne version `3.0.0` saine. La migration fictive est absente après restauration ; `controle-donnees` est identique avant/après (`ok=true`, tables, état et documents). Les 49 tests Python, les 4 tests de publication, ShellCheck, la syntaxe Bash et le formatage des documents passent. Cette recette isolée utilise exclusivement des données de test et des images locales ; elle ne constitue pas une validation des futures signatures de publication.

La CI du commit `f6a52bb` valide qualité, 587 tests Vitest, CodeQL, scans HIGH/CRITICAL, installation Ubuntu vierge et montée de version dans le vrai conteneur, restauration comprise.
